# Dataset assessment for NIDRA — 2026-09-20

Question: should a second dataset be added to the CIC-IDS2017 pipeline, and if so which one? The bar is not "more attacks" but a **valid temporal mapping**: per-host state sequences at minute resolution with an attack *onset* that can be placed in time, so that the forecasting target (`P(attack begins within h minutes | history)`, `nidra/data/onset.py`) is meaningful. A dataset that only supports "is this flow malicious" adds detection data to a forecasting project, which is scope drift (CLAUDE.md, "When adding features", item 1).

No dataset was downloaded for this assessment. Every statement below is about the published format of each dataset; nothing here reports a measurement on it.

## What CIC-IDS2017 gives, and what it lacks

| Property | CIC-IDS2017 (in use) |
|---|---|
| Telemetry | pcap (packets) + CICFlowMeter CSV (flows) with `Source IP`, `Timestamp`, `Label` |
| Timestamp resolution | **minute** in the TrafficLabelling CSVs (D/M/YYYY H:MM); packet timestamps are microsecond |
| Per-host sequences | yes — one source IP over a working day, 8 day-files |
| Attack onsets | 14 labelled attack types on 4 days, each a scripted episode with a known start; the episode boundaries are derived from the flow labels (`merge_episodes`) |
| Precursor structure | **thin**: the attacks are launched from the attacker VM without a preceding reconnaissance phase on the same source host; pre-onset windows within 30 min: train 69, val 27–30, test 327, holdout 73 (`artifacts/metadata/data_audit_w60.json`) |
| Families available for generalisation | train: FTP-Patator, DoS×4; val: SSH-Patator, Heartbleed; test: Bot, PortScan, DDoS; holdout: Web×3, Infiltration — every evaluation family is unseen in training by construction |

The limiting factor for the forecasting claim is the last-but-one row: the dataset has few genuine precursors, so Task B (onset forecasting) is evaluated on tens of positives. A second dataset is worth adding **only** if it supplies onsets with observable run-up on the same host.

## Candidates

### CSE-CIC-IDS2018 — do not add

- Same generator family as 2017 (CICFlowMeter, same 12-hour-clock timestamp defect, same scripted attack days), so it adds volume, not a different kind of evidence.
- ~220 GB of pcaps on AWS; ten day-files. It was already tried once for this project and abandoned for build-time reasons (CLAUDE.md: "Do not switch to CSE-CIC-IDS2018").
- Attack scheduling is the same "attacker VM starts tool at time T" pattern, so the precursor problem is identical.
- **Decision: excluded.** The dormant label rules in `nidra/data/labels.py` stay dormant.

### CTU-13 (Stratosphere IPS, 13 botnet scenarios) — a real candidate, not added in this cycle

- Telemetry: pcap per scenario (the full pcaps are only published for the botnet traffic; the complete captures are partly withheld for privacy) plus **Argus bidirectional NetFlow** (`binetflow`) with `StartTime` at millisecond resolution, `SrcAddr`, `DstAddr`, `Dur`, `TotPkts`, `TotBytes`, `SrcBytes`, `State`, and a per-flow `Label` (`flow=From-Botnet-…`, `flow=Background-…`, `flow=To-Botnet-…`).
- Temporal mapping: **valid**. Each scenario is one capture of a known botnet (Neris, Rbot, Virut, Menti, Sogou, Murlo, NSIS.ay) with the infected host(s) named per scenario; the infection and the C&C/spam/click-fraud phases follow each other on the same source host — i.e. real per-host progression, which is exactly what CIC-IDS2017 lacks.
- Cost: the 15 flow features would have to be rebuilt from Argus fields (Argus reports connection `State`, not per-flag counts; IAT columns are absent), or from the botnet pcaps with `flow_assemble.py`, which would then not include the background traffic. Packet features (11) need the full pcaps, which are not all public. Stage labels: `c2` for the botnet phases; the six-bucket taxonomy has no "spam"/"click-fraud" bucket (they would be Impact-like, i.e. `exfil` under the current documented simplification).
- **Decision: candidate for a follow-up cycle** with a scoped plan: scenarios 1, 2, 9 (Neris, with spam + C&C phases) through the pcap path only; flow-only mode for the 11 packet features where pcaps are withheld, reported as such. Not started here because the run would land in the same compute window as the Δ=60 retrain and would be flow-only for most of the data.

### UNSW-NB15 — not suitable for the forecasting target

- Telemetry: pcap + Argus/Bro-derived CSV with `Stime`/`Ltime` (second resolution), `srcip`, `attack_cat`, `Label`; 9 attack categories generated by the IXIA PerfectStorm tool on a testbed.
- Temporal mapping: **not valid for onsets**. Attacks are injected by the traffic generator interleaved with normal traffic in short bursts with no per-host progression; the "attacker" IPs are the generator's, and there is no run-up on a host that could be forecast. The dataset supports cross-dataset *detection* evaluation (Task A) only.
- **Decision: excluded for forecasting.** Could serve as an out-of-distribution detection check for the risk head, which is not the claim under evaluation.

## Consequence for the claims

Claims stay scoped to CIC-IDS2017. Where the final report states generalisation, it means: attack families never seen in training (Friday's Bot/PortScan/DDoS and Thursday's Web/Infiltration) and the leave-family-out analysis inside the training days — not cross-dataset transfer. That limitation is stated in the model card.
